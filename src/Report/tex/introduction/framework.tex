\section{Framework}
\subsection{Software Development Methodology}
\label{sec:dev_method}
As this project has been very time restricted, the development needed be as
efficient as possible. We therefore had to find a model that utilized the
manpower we had available in the best possible way.
The size of the group was quite small, so big and complex development models
would add too much bureaucracy to coordinate the project and was thus overkill.

As we wanted to have a lightweight development model, some form of an
agile\cite{AGILE} development model with a set of development cycles was
preferred. This way, each group member could take an active part in the project
and all members could feel a sense of ownership.

Developing iterative and incrementally, we got the best from both the
agile development world and from the very well defined waterfall
approach\cite{waterfall}.
We were able to get feedback throughout the project, and have a structured and
reasonable way of actually doing changes to the plan while the project was running. At the
same time we could be able to maintain the overall plan within cycles, so that
it was possible to work individually, while still being well coordinated.

To be able to develop all the modules of the project within the timeframe, each development
cycle consisted of multiple modules or functionality developed in parallel. This
allowed us to maximize our utilization of time and personnel.

The start of each cycle consisted of a meeting where we defined the goals for
that cycle and identifying the individual tasks that we needed to get
done. This is similar to the start of a sprint in the development model
Scrum\cite{scrum}.

In the development part of the cycle, we worked individually on the tasks that
were defined in the planning. Regular meetings and cooperative programming
within the group ensured that we all pulled the project in the same direction.

At the end of each cycle we would have a working set of software, which ideally
complied with all the goals set in the start of each cycle. We held meetings
with Avdeling BKI between each cycle to present the progress, and to let them
influence the direction of the project.

After all the development cycles had been completed, we then made a final
assurances that everything worked as intended and that all modules coexisted in
harmony. This part of the development also consisted of some hands-on testing by
the client and performance testing.

\subsection{Schedule}
We planned this project to have a fairly comprehensive initial phase for mapping
and designing of the system. We spent the better part of the first two weeks
figuring out how to implement the system. After the two weeks and before we
started actually programming, we held a ``project decision meeting" with the client to confirm
that we had modelled the system correctly, to get feedback and to get the final
go-ahead.

We then began the implementation phase which consisted of development cycles as
described above in section \ref{sec:dev_method}. This phase was devided into
five parts, consisting of four development cycles and a final cleanup/testing cycle. All the development cycles
lasted two weeks, aside from the last development cycle and the cleanup/testing
cycle, which lasted one week each. 

During those cycles we conducted meetings with both our mentor and our client
every two weeks, timed so that these meetings took place on alternating weeks.
This ensured that we got continual feedback and advice throughout the entire
process. 

After these weeks, we completely shifted focus from the software to the project
report and spent the final 5-6 weeks working on that. Because we had done a
thorough job during the first few weeks of the project, we had a lot of the
contents for the report more or less created.

\subsection{Project Organization}
We organized the project work a little differently throughout the project,
reflecting on the fact that we had multiple phases. During the first few weeks
we spent most of the time together in a group room, working together and discussing things.
Once most things had been worked out and the implementation phase began, there
was more room and need to work individually to produce code. We still gathered 
together every so often to syncronize our progress and plan the next course of
action.

Throughout the project, most decisions have been met either by confering with
the client or achieving consensus within the group.
