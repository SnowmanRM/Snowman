\section{Update module}
The purpose of the Update module is to fetch and read rules and configuration
files from external sources, and populate the database with this information.
Effectiveness in updates is a key issue, and a number of deliberate
optimizations for performing updates, with the goal of saving time by omitting
unnecessary operations, are explained in the following sections.

The term Update is used to refer to the actual module, including all its classes
and functions. To avoid confusion with the module, the term \em update-package
\em is specifically used to refer to update data coming from external sources.

This section will define an example rule to be used throughout subsequent
sections and the remainder of the chapter, to illustrate the lifespan of a rule
in the system.

Word: rulestring.

\subsection{Sources}
A \em source \em is used by Update to determine where the update-package is
located. Normally this is on a remote site, and the source contains the URL
pointing to the location of the update-package. A source can be configured to
update at regular intervals, or the user can run an update manually on a source.
To make the update process more effective, Update makes use of an MD5 URL which points to
a file containing the MD5 hash of the update-package. This hash is stored for
every source (if available) and is compared to any pre-existing hash to verify
if the system is up to date or not. Update will only download and process an
update-package when it encounters a new hash.

\subsection{Running an update}
As an example scenario, consider a rule (name, figure reference, source,
ruleset etc.). An update is triggered on the source at the predefined time

The update is cancelled if the source is already up to date; the MD5-hashes of
the latest update in the database, if any, and the latest update on the remote
site are compared, and the process is terminated if these hashes are
identical. Otherwise, the update is downloaded to a temporary directory and the
update process continues. A file can be a tar-archive containing an arbitrary
number of rulesets and configuration files, or it can be a plain text file
containing Snort configuration (?).

The tar-archive is extracted, and the update module recursively parses each
file in each folder. In most cases the update-package will contain only minor
changes in relation to its predecessor, e.g. only one file is different in the
latest package, and parsing all files that has not changed would therefore be
a waste. To address this issue and save processing time, the name, path and
MD5-hash of every file is stored in the database per source. Every time the
update module parses a file, it first creates a hash of the file and
compares this with the respective file's hash in the database. If the file
is present in the database and the two hashes coincide, the file is
considered \em not new \em and is skipped. The following sections will elaborate
on the parsing of files based on file type.

\subsubsection{Rule sets}
A rule always belogs to a ruleset which can be specified in the raw
rulestring. If the parser does not find this attribute in the rulestring,
the filename is considered to be the ruleset name.

\subsubsection{Threshold}
A rule threshold defines a limit and/or threshold for the triggering of a
specific rule, and can exist as an inline or standalone option.
Rule thresholds are deprecated, and support for this functionality will cease in a
future version of Snort\textregistered, where it is replaced by \em detection
filters \em and \em event filters \em (see below) \cite{SnortManual}. To
maintain compatibility with current rules, Snowman supports reading inline and
standalone threshold definitions.
