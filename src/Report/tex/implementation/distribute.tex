\section{Distribute}
To distribute the rules from the central database to the sensors in a format
that the snort-software can understand, three major things happen. Each of these
is covered in the following three subsections:

\subsection{Initiating the distribute}

Before a synhronization can start, the sensors would need to know that they
should synchronize. There are mainly two things that can cause a synchronize to
start:
\begin{enumerate}
  \item Automatic synchronization based on time
  \item Manually invoked trough the webinterface on the \snowman-server.
\end{enumerate}

In the first case, the client itself knows that it should start to synchronize,
and therefor just starts the authentication/synchronization procedure with the
server. 

In the latter case, the client does not initially know that anything happened as
the central server is what hosts the webinterface. The central server then
contacts the client via the ``snowmanclientd'' daemon, telling it to initiate a
synchronization.

\subsection{Synchronization}

When a synchronization is initiated, the client starts with connecting to the
``snowmand'' daemon on the sentral server, and authenticate with it. If the
authentication is successfull, the server knows the sensor, and which rules the
sensor should get installed, and we can then start the synchronization.

The first thing that is done is to retrieve all the RuleClass objects, and
update the local cache to correspond to the retrieved list. Changed objects will
be updated, new objects inserted into the local database, and obsolete objects
will be deleted. Next lists of Generators, RuleReferenceTypes and RuleSets is
retrieved, and the local database is updated in a simmilar manner as with the
RuleClass objects.

For the synchronization of the rule themselves, which is the main bulk of the
data needed to be synchronized, a more efficient approach is done. First a list
over the signature-id's and revisions of the rules that should be present on the
sensor is retrieved. If rules in the local cache is not mentioned in this list,
or this list indicates that a new version of this rule is available, the rule is
deleted from the local cache. Eventual tuning-parametres belonging to this rule
is also removed.

Next, the client starts to request the rules that it currently is missing from
the server. To speed things up, this happens in bulks of 250 rules per request.
This way, no requests gets too big and time-consuming, while we do not use too
many requests of lots of things have changed. For the rules requested,
tuning-parametres like filters and suppress is supplied if the rule have any
such applied on the given sensor. References is also passed along with the rule.

All the recieved rules is then saved to the local database, and the
synchronization is complete. The final step of generating snort
configuration-files is then started.

\subsection{Generating snort configuration}
The generation of the snort configuration-files is a rather simple process.
First, the old configuration is cleared out, and new files are generated based
on the content of the local database.

The naming-convention of the files is simmilar to the one SourceFire supplies
their rulesets, and the format of the files are exactly the same. This is done
to simplify the visual inspection of the rulefiles, if that is desirable. Snort
in it self does not really care of the configuration-files to be in a certain
order, as long as the content can be recognized as snort-configuration.

In addition to the various files created by snowman, a certain file is
guaranteed to be generated. That is the ``snowman-includes.cfg'' file, which
names all the files generated. If snort includes that file, all the files
generated by snowman will be included by the snort software.

Finally, when the configuration is generated, the snowman-client sends a SIGHUP
signal to the snort-process, which makes snort reload its configuration, and
start using its new ruleset.
