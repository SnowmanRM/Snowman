\section{General Design}

This section is deicated to the discussion of the general design of \snowman{}.

\subsection{Centralized or distributed setup?}
We decided early to create \snowman{} in such a way that it can be set up in a
distributed manner. The main considerations behind this choise is the
bandwidth-requirement needed by the rule-updates, and the load of the central
server.

\begin{figure}[h]
	\includegraphics[width=130mm]{./img/Architecture.png}
	\caption{General architecture}
	\label{fig:general_architecture}
\end{figure}

On figure \ref{fig:general_architecture} you can see the difference between
central and distributed setup. The red dotted lines represent the communication
in a centralized setup, while the blue lines between the server and the clients
represent the communication in a distributed setup.

\subsubsection{Bandwidth requirements} 
The \snort{} sensors managed by \snowman{} might have very varying
network-infrastructure connecting them to the central server. In worst case, the
sensor might be placed at a military-base in the field, on the other side of the
planet, only connected to the central server via a sattelite-connection with
limited capabilities for transmitting data. As the rulesets applied to sensors
typically is tens of thousands rules, and the changes between two versions of
the sets typically affects about a thousand of them, it seems reasonable to only
copy the changes when an update should be done.

\subsubsection{Central server load}
When a full update of all the sensors is requested, new rule-sets would be
needed to be created, and distributed to the sensors.

In a centralized enviorment, the \snowman{} server would need to generate all
the new rule-sets, and send them to the client. The server would not known on
beforehand which rules currently exists on the sensor, so a full list of rules
would need to be sent. Even if not a single rule changed. Also, if the sensor
for some reason is unavailable, or connected trough a unreliable
network-connection, the central server would need to put down quite some effort
to send the rules to the sensor. Again, even if it is not neccesary as no rules
have changed.

In a distributed eniorment, we would be able to put some logic (a client) onto
the machines hosting the sensors. This way, when an update is occouring, the
client can get a list of rule-ID's from the central server, and self be
responsible for collecting the new revision of the rules that have changed, or
is missing. This way, the central server would only need to collect the full
rules from the database if the rule actually is needed by the sensor.
