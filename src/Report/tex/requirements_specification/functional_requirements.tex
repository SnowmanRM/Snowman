\section{Functional Requirements}

\subsection{Program Workflow}
\label{sec:program_workflow}
To develop our requirements, we decided to chart the program workflow in order
to better understand what the system is expected to do. Since this was to be a
highly user-oriented system we accomplished this by going over the old system,
BHTB, step by step with the client and detailing the functions and various needs
for improvement or additional functionality. From this, we developed a workflow
chart that reveals the major system parts. This is in addition to taking into
account the management process outlined in Henriksens thesis\cite{BHTB}.

\begin{figure}[ht!]
\includegraphics[width=130mm]{./img/program_workflow.png}
\caption{Program Workflow}
\label{fig:program_workflow}
\end{figure}

To explain the workflow chart in figure \ref{fig:program_workflow}, the blue
boxes are the major system functionalities, the green boxes are the major goals of the system and the
arrows show the direction of flow the system should have.

As you can see, if you trace the arrows, all of the program flow ends up with
rules being syncronized to the sensors. This, of course, makes sense
since that is the whole purpose of the system to begin with.

But the road to Rome consisted of a lot more functionality that needed to be in
place, and that interacts with the rules, before they are ready to be handed
over to Snort.

It's important to note that very early on, we decided that writing rules,
automatically check them for errors and commenting them were nice-to-have (but
still important) features that we could implement if we had time to do so. Hence
they are greyed out in the drawings, and as you will notice further on in the
report, was never developed due to time contraints.

From this workflow we could outline a rough modular design (figure
\ref{fig:program_modules}) based on the naturally separate functions of updating
rules, tuning them, distributing them and show them. We also added a database module, since most of our program was
going to be centered around it.

\begin{figure}[ht!]
\includegraphics[width=130mm]{./img/program_modules.png}
\caption{Program Modules}
\label{fig:program_modules}
\end{figure}

\subsubsection{Rule Downloading Module}
This module will handle all functionality related to downloading rules,
including comparing MD5 checksums.
\subsubsection{Rule Pre-Storage Processing Module}
This module will essentially take downloaded rules, and parse and process them
into objects that can be fed into the database.
\subsubsection{DB Module}
This module will handle all input and output to/from the database.
\subsubsection{Rule Pre-Distribution Processing Module}
This module will essentially take rules stored in the database and prepare them for
distribution to sensors.
\subsubsection{Rule Distribution Module}
This module will be in charge of distributing rules out to the Snort sensors and
handing the rules over to Snort itself.
\subsubsection{Tuning Module}
This module will handle all functionality related to turning rules on or off,
filtering them or suppressing them.
\subsubsection{Rule View Module}
This module will contain all the functionality needed to display the system
status and system functions to the user. It will be the primary way the user
interacts with the system. Basically the GUI module.
\subsubsection{Daemon Module}
This module will run continually on the system to ensure that the system is
responsive and to carry out any interval based tasks, such as automatic updates or distributions.
\subsubsection{Commenting Module}
This module will allow users to attach comments to rules.
\subsubsection{Rule Writing Module}
This module will handle functionality for writing custom rules and editing existing rules.
\subsubsection{Automatic Rule Checking Module}
This module will be responsible for verifying rules to ensure that there are no malformed or
misconfigured rules that may potentially break or cause a halt on a Snort
sensor.

\subsection{Domain Model}
After outlining all the things above, we put together the concept model in
figure \ref{fig:conceptual_class_diagram} of the objects we would need in the
system. Even though a Snort rule is quite simple in and of itself, there are a lot of meta information surrounding them, like rule
revisions and rule classes.
Thus our system needed at least 16 different classes in order to fullfil the
basics of the required functionality.
