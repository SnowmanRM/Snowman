\section{Project Background}
The Norwegian Armed Forces Cyber Defense (CYFOR) unit for Computer Network Defense
(CND), Avdeling BKI, is responsible for detecting and stopping cyber-attacks against the
critical infrastructure and command and control systems utilized by the Norwegian military.
One of the tools used to carry out this task is the open source Intrusion
Detection System (IDS) \snort{} \cite{Snort}.

\snort{} is a leading open source IDS that is used to detect potentially unwanted
or malicious network traffic based on predefined patterns described in signatures. There are both
free and commercial signatures available for \snort{} and as \snort{} has been highly
adopted by the security community, these signatures are continually updated and maintained.
Using \snort{} has been plagued for years by the fact that it does not have a good
system for handling, updating or maintaining the signatures (henceforth called rules and rule sets) used
for detection, thus making it cumbersome to utilize \snort{} for security analysts.

Avdeling BKI has therefore tasked a group of students from GUC to design and develop a
more complete, effective and secure rule management system for \snort{} that can
continue to live on beyond this project.

\section{Previous Work}
Research \cite{BHTB} has shown that a good rule management system for \snort{}
will improve the workflow and efficiency of the IDS significantly and a prototype for such a system was built
in 2012 called Bring Home The Bacon (BHTB) \cite{BHTB}. This prototype has been
in use at Avdeling BKI since 2012, but is suffering from lacks in functionality
and efficiency due to being a proof-of-concept prototype. The prototype did,
however, prove that there is a significant gain from having an intuitive
Graphical User Interface (GUI). The operators workflow becomes much more
efficient, as you go from having to do complex operations in a Command Line
Interface (CLI) to just pushing buttons to make the system do
things automagically.

There was another similar project conducted at Gjøvik University College (GUC)
in 2012 called \snortmanager{} \cite{SnortManager} that also deals with
managing \snort{} rules.
However, that project was not properly released as open source software. The
project files are available but there is no documentation or instructions
publically available that describes usage and installation. The project has
also not been maintained since its initial release and is designed for a
specific company in mind.

Enabling, disabling and
configuring rules is also cumbersome in this system as it is based on plaintext
arguments in ``policies'' that users must construct themselves. The rule distribution is also done manually
from the files generated. This makes \snortmanager{} something not very usable
for Avdeling BKI and their routines.

There are also other software available in the \snort{} community that work very
well for that they do, but are limited in their scopes are more suited for
smaller, single sensor implementations of \snort{}. Good examples of these
are Pulled\_Pork\footnote{https://code.google.com/p/pulledpork/} and
Oinkmaster\footnote{http://oinkmaster.sourceforge.net/}.

The key differences between all these pieces of software and \snowman{} will be
explained in more detail in chapter 2.

\section{Target Audence}
The software this project has produced is targeted at users of \snort{} as an IDS.
More specifically, this target audience usually consists of security experts
with a high degree of knowledge of \snort{} and computers in general.

This report is targeted at those that may be interested in discovering just how
complex the rule structure of \snort{} really is, and academics that are interested
in reading about software complexity versus efficiency.

\section{Project Objectives}
\subsection{Result Objectives}
We reiterate from the project plan[link to project plan] that this
project has a goal of researching, designing and developing a system that
as a minimum:
\begin{itemize}
\item Is more efficient than BHTB.
\item Is developed as an engine that responds to API calls from any arbitrary
user interface.
\item Is modular in design and allows future changes and additions to not affect
existing functionality.
\item Is scalable enough to handle both small and large sets of IDS sensors and
rules in a production environment.
\item Is able to download rules and rule sets from multiple customizable sources.
\item Is able to distribute different rules to different IDS sensors.
\item Can download and distribute rules automatically at set intervals.
\item Is capable of exporting rules for sharing.
\item Has the capability to activate, deactivate, filter and suppress rules on a
per sensor basis, in a way that is user friendly.
\item Supports multi-user interaction.
\item Can efficiently and safely work with different installations of \snort{} and various
other third party tools, such as SNORBY\footnote{http://snorby.org}.
\item Is easy to install.
\item Has an internal logging system.
\item Is well documented and can be easily adopted by anyone as open source software.
\end{itemize}
In addition, the project will attempt to add the following functionality if
time permitting:
\begin{itemize}
\item A graphical user interface.
\item Said user interface must be user friendly and intuitive, and require only
limited knowledge of \snort{} rules from the user.
\item The system can also distribute rules to
Suricata\footnote{http://suricata-ids.org}, another \snort{}-like IDS, which
can operate with the exact same rules as \snort{}.
\item Implement security features that ensure confidentiality of rules.
\item The project will investigate and potentially implement multi-threading
technology or other optimization techniques to exploit modern hardware
capacities.
\item The system is capable of validating and checking rules for errors before
they are distributed to sensors.
\item The system supports commenting of the rules.
\item The system supports writing custom rules and editing existing rules.
\end{itemize}
Once the system has been developed, it will be released as an Open Source Software to the
public in a well-documented format.
\subsection{Effect Objectives}
Forming baselines from the current prototype \bhtb{} and from \snortmanager{},
the project has a goal to further increase the efficiency of rule management by investigating and
implementing programming techniques such as multi-threading and a change-based system to
reduce latency and delays in the system by as much as 50\%.

As a very minimum the software efficiency must be linear or better, meaning if 1
action takes 1 second, 10 actions must take 10 or less seconds.

The project will therefore be measuring for these effects.

\section{Project Description}
In broad strokes, this project has been about designing a system that provides a
simple and efficient way of handeling rule management for the \snort{} IDS. The
project is the spiritual successor to \bhtb{}. Essentially taking good ideas
from \bhtb{}, adding a few of our own, and creating a more adoptable open source
rule management system for \snort{}.

We utilized the latest stable version of Python as the main programming language
for the project, which is version 2.7. C++ was also considered, but due to the
limited time at our disposal, we felt we could create more functionality with Python, due to it requiring less
memory management and the general “programmer friendly” ways of doing things.

The system required a database to function efficiently and the project
primarily utilizes MySQL, as it is the de facto standard for the Linux
platform. Furthermore, the project also consisted of creating a GUI that is user
friendly and responsive. 

The software that was created in this project, though still lacking some
features and contains some minor bugs, largely fulfils the project goals
outlined above. We did not fulfil the goal of producing software that has
reduced latency and delays, but we are confident that this is because we have
sacrificed efficiency for functionality. We also feel that the functionality
gained outweighs the efficiency lost and the efficiency curve is still very much
within the linearity objective, as you can read about in chapter \ref{chap:}.

\section{Framework}
\subsection{Software Development Methodology}
As this project has been very time-restricted, the development should be as
efficient as possible. We therefore needed a model that utilized the manpower we
had available in the best possible way.
The size of the group was quite small, so big and complex development models
would add too much bureaucracy to coordinate the project and was thus overkill.

As we wanted to have a lightweight development-model, some form of an agile
development model with well-defined development-cycles was preferred. This way,
each group-member could take an active part in the project and all members could
feel a sense of ownership.

Developing iterative and incrementally, we got the best from both the
unstructured world, and from the very well defined waterfall approach. We were
able to get feedback during the project, and have a structured and reasonable
way of actually doing changes to the plan while the project was running. At the
same time we could be able to maintain the overall plan within cycles, so that
it was possible to work individually, while still being well coordinated.

To be able to develop all the modules of the project within the timeframe, each development
cycle consisted of multiple modules developed in parallel. This allowed us to
maximize our utilization of time and personnel.

The start of each cycle consisted of a meeting where we defined the goals for
that cycle, and identification of the individual tasks that we needed to get
done. This is similar to the start of a sprint in the development model Scrum.

In the development part of the cycle, we individually worked on the tasks that
were defined in the planning-part. Regular meetings and cooperative programming within the group would
ensure that we all pulled the project in the same direction.

At the end of each cycle we would have a working set of software, which ideally
complied with all the goals set in the start of each cycle. We planned to
have meetings with Avdeling BKI between each cycle to present the progress, and
to let them influence the direction of the project.

After all development cycles had been completed, we then made a final
assurances that everything worked as intended and that all modules coexisted in
harmony. This part of the development also consisted of hands-on testing by the
client and various performance testing.

\subsection{Schedule}
We planned this project to have a fairly comprehensive initial phase for mapping
and designing of the system. We spent the better part of the first two weeks
figuring out how to implement the system. After the two weeks, we went to our
client and presented our work for their feedback and a final go-ahead before we
began programming.

We then began the implementation phase which consisted of development cycles as
described above. This phase was devided into five parts, consisting of four
development cycles and a final cleanup/testing cycle. All the development cycles
lasted two weeks, aside from the last development cycle and the cleanup/testing
cycle, which lasted one week each. 

During those cycles we conducted meetings with both our mentor and our client
every two weeks, timed so that these meetings took place on alternating weeks.
This ensured that we got continual feedback and advice throughout the entire
process. 

After these weeks, we completely shifted focus from the software to the project
report and spent the final 5-6 weeks working on that. Because we had done a
thorough job during the first few weeks of the project, we had a lot of the
contents for the report more or less created.

\subsection{Project Organization}
We organized the project work a little differently throughout the project,
reflecting that we had multiple phases. During the first few weeks we spent most
of the time together in a group room, working together and discussing things.
Once most things had been planned out and the implementation phase began, there
was more room and need to work individually to produce code. We still gathered 
together every so often to syncronize our progress and plan the next course.

Throughout the project, most decisions have been met either by confering with
the client or achieving consensus within the group. At no point during the
project has there been a need to enforce the project rules.
